# Harmony360 Architecture

Harmony360 is designed as one governed runtime serving multiple products.

## Canonical workflow

```text
Customer Intake
→ Project Creation
→ Asset Upload
→ Inventory and Hashing
→ Content Extraction
→ Evidence Registration
→ Classification and Relationship Detection
→ Reconciliation
→ Governance Review
→ Blueprint Generation
→ Report Rendering
→ Delivery and Audit Preservation
```

## Runtime boundary

The runtime distinguishes among:

- deterministic computation
- evidence-grounded inference
- probabilistic assistance
- human judgment
- research-only constructs

No symbolic, mathematical, philosophical, generated, or historical source becomes an operational control merely because it exists. Promotion requires evidence, defined interfaces, validation, tests, governance review, and a recorded decision.

## Core bounded contexts

- Identity and Access
- Customer and Billing
- Project Management
- Asset Ingestion
- Content Extraction
- Evidence and Lineage
- Intelligence and Classification
- Reconciliation and RECL
- Governance and Promotion
- Blueprint and Product Templates
- Reporting and Delivery
- Operations and Observability
- Canonical Knowledge Archive

## Product-runtime relationship

```text
Shared governed runtime
        ↓
Product configuration
        ↓
Customer workflow
        ↓
Governed deliverable
```

Product templates may depend on shared domain services. Shared services must not depend on a specific product template.
