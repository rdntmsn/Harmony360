# Harmony360

**From scattered knowledge to governed systems, blueprints, and products.**

Harmony360 is a governed knowledge and product-building framework for recovering signal from fragmented files, notes, chats, research, archives, and unfinished projects, then turning that material into evidence-linked blueprints, systems, offers, and implementation paths.

Harmony360 is built around a simple operating logic:

```text
Recover → Index → Discover → Register → Reconcile → Generate → Validate → Snapshot
```

The platform is designed so retrieval relevance never becomes authority by accident. Evidence, provenance, lineage, typed divergence, Guardian review, promotion decisions, reconstruction, and governed snapshots remain explicit parts of the runtime.

Typical source material includes:

- documents and folders
- notes and chats

- unfinished projects
- duplicated or forked work

Harmony360 processes that material into structures such as:

- evidence records
- source and authority mappings
- lineage records
- knowledge registries
- divergence and reconciliation records
- governed blueprints
- decision and reconstruction trails
- launch-ready product packages

## Runtime architecture

The current engineering direction follows **One Runtime, Many Products**.

```text
Client / Source Material
        ↓
Intake + Asset Archaeology
        ↓
Canonical / Extended / Deferred Knowledge
        ↓
Governed Retrieval
        ↓
Evidence Registration
        ↓
Observed State
        ↓
RECL
        ↓
Guardian
        ↓
Promotion Decision
        ↓
Registry + Reconstruction
        ↓
Lineage / Audit / .har360 Snapshot
        ↓
Product Deliverable
```

The runtime is intentionally designed around deterministic rules first, with probabilistic or LLM assistance treated as an optional enhancement layer rather than a foundational dependency.

## Engineering principles

Harmony360 engineering follows these boundaries:

1. Evidence before assertion.
2. Lineage before promotion.
3. Governance before automation.
4. Deterministic rules before probabilistic assistance.
5. Retrieval relevance is not knowledge authority.
6. Agents and providers operate inside the runtime; they do not own governance ledgers.
7. Canonicalization requires an explicit governed decision.
8. One runtime can power multiple products.
